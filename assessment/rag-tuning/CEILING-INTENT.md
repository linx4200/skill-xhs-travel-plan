# 天花板基准（B3-ceiling）— Agent 执行意图说明书

本文档是「按批次挑选、合成一份天花板基准」任务的**意图冻结件**，由 2026-09-20 的采访结论固化而成。
与 `INTENT.md`（自动调参意图）、`USAGE_GUIDELINE.md`（怎么用评估体系）、`RAG_TUNING_TECHNICAL_PLAN.md`（技术方案）并列：
本文档回答的是**「为什么建天花板、它长什么样、怎么建、哪些不许动」**。

---

## 0. 任务一句话

把 `outputs/` 下多个历史批次按「基底批次 + 人工覆盖清单」合成一份**天花板基准 B3**，
它代表「我见过的、人工认定的最好产出」，用作**调参的目标函数**（越接近越好）。

## 1. 定位：天花板，不是地板

| 维度 | 现有 B1 / B2 | B3-ceiling |
|---|---|---|
| 语义 | **地板**：验收线。critical 丢失即 FAIL | **天花板**：目标函数。没人能全覆盖是正常状态 |
| 来源 | 单个满意产物的 facts 派生 | 基底批次 + 人工覆盖清单合成 |
| 结论用法 | 通过 / 不通过 | **覆盖率 + 缺口清单 + 排序**，不做通过判定 |
| 是否可改 | 冻结（改要走 `assessment:upgrade` 升版本） | 一次性冻结；**保留用户显式要求更新的能力** |

**用户原话**：「这一份 baseline 应该作为天花板来处理，而不是地板。」

**推论（已确认）**：B3 与 B1/B2 **并存**，不取代任何一方。§1.3「明确优于基线」的判定仍按地板基准走；B3 只回答「离理想还差多少」。

## 2. 覆盖层级与计分口径

### 2.1 三层都覆盖

| 层 | 内容 | 谁定 |
|---|---|---|
| 检索层 | 哪些 key chunk 必须进阅读池 | **自动派生**（见 §5） |
| facts 层 | 材料被整理成哪些信息点 | **用户手工定**（唯一要填的） |
| 呈现层 | 内容该出现在哪一页、页面结构 | **自动派生**（见 §5） |

### 2.2 分层给分，不混总分

- 检索层 / facts 层 / 呈现层**各自出一个分数**，不合成单一总分。
- **调 RAG 参数时只看前两层**。理由：三层混成一个总分时，模板与渲染的波动会注入噪声，污染检索参数的排序。
- 每层给**两套数字**：无条件覆盖率（分母 = 全部天花板条目，衡量材料广度）与
  **层内转化率**（分母 = 上游已覆盖的条目，衡量这一层自己的漏损）。两者不可互相替代，
  细则与理由见 §6.2。

## 3. 选择模型：基底批次 + 覆盖清单

**不再逐格决策。** 模型为两段：

1. **基底批次（base）**：`2026-guoqing-self-drive-plan-20260907`（= 现有 B2 基线的来源批，同源可比）。
   基底的**全量内容**作为默认值。
2. **覆盖清单（coverage）**：用户在空白表里**手写指针**，只写「要改的那几格」。留空 = 采用基底原样。

### 3.1 挑选单位

单位 = **(类型, 目标, 部分)**，即 facts 结构里的一格。例：`景点-九洞天景区-门票`。

> 用户原话举例：`20260918 - 城市 - 昭通 - 备选景点库`。
> 注：采访中用户曾用 `0829 - day1 - 路线部分` 举例，追问后确认那只是随手举例 —— **组织轴是景点/城市，不是天**。

### 3.2 指针格式（用户在清单里写的形式）

**范围列**回答「改哪一格」，**改用列**回答「换成什么」。改写列支持四种动作：

```text
① 整格替换（默认）   改用列 = 批次 - 类型 - 目标 - 部分
② 只取来源的某些条   改用列 = 批次 - 类型 - 目标 - 部分 #1,3        （#N 为 1-based 条号，可写 #2-4）
③ 把来源的条并进基底 改用列 = 合并 批次 - 类型 - 目标 - 部分 #1      （基底条目在前，来源条目追加在后，按值去重）
④ 整目标接管        范围列留空，改用列 = 接管 批次 - 类型 - 目标      （该目标所有内容字段取自来源；只支持 景点/城市）
```

- **动作前缀**：`替换`（= 默认）/ `合并` / `接管`，同义词 `覆盖` / `追加` / `整取`；前缀可省略。
- **批次**：见 §8 的批次标签表。必须精确匹配；前缀有歧义时报错并列出候选（`20260918-3` 不会被 `20260918` 吃掉）。
- **类型**：`景点` | `城市` | `天` | `全局`（也接受 `place`/`city`/`day`/`global`）。
- **目标**：中文名（如 `九洞天景区`）；天层写 `day-01` 或 `第1天` 或 `1`；全局层写 `-` 或 `*`。
- **部分**：字段名，**中文名或 JSON 键名都接受**（映射表见 §4.1）。除精确匹配外还有**包含兜底**，所以 `门票与优惠`→`tickets`、`推荐游玩线路`→`routes`、`不同玩法/游玩方式`→`play_options` 都能认。
- **备注**：允许自然语言。例：「保留价格，删掉小程序那条」。agent 按备注执行；无法执行时**必须回问**，不得自行取舍。
- 分隔符宽容：`-`、`·`、`|`、`｜`、`/`、`>` 均可；前后空格忽略。
- **删除**：改用列填 `删除` / `skip` / `无`（范围列必须写明部分）→ 该格从天花板中剔除。
- **歧义即拦下**（不静默跳过）：同一格写两次、条号越界、来源该格为空、部分名无法识别、类型不一致 —— 全部报错并中止，除非显式加 `--allow-partial`。

回报格式要求：每次生成后在回复里列出「哪几行按哪种动作执行了什么」，把注释型备注（如第 9 行 `景点 - 盐津老县城 - 看点` 的「基底批次包含了不是【看点】却是【美食】的信息」）与**需要用户裁决的备注**分开说 —— 前者只解释动机，不阻塞执行。

### 3.3 覆盖清单是**完全空白**的

用户明确要求：**不预填候选内容，也不预填基底现状**。

> 用户原话：「你不需要给我列出其他批次现状，也不需要列出基地批次的现状，我就指定给你就好了，我会自己看。」

因此模板只给：格式说明 + 空表。可选格子菜单（§4.2）**作为独立附录**提供，只列名字不列内容。

## 5. 派生规则（检索层 / 呈现层）

**按格子实际来源派生**，不是一律按基底派生。

- 某格改用批次 X → 该格的证据 chunk 与页面归位**都取 X 当时的**。
- 目的：保证**内容与证据同源**，不出现「内容来自 0918、证据来自 0907」的错配。

具体实现：

1. **检索层**：以基底批次的 `retrieval-workspace.json` 为骨架；对被覆盖的每一格，按
   `(类型, 目标, 主题)` 把来源批次的 `themes[主题]` 条目与 `unique_chunk_ids` 并进来，
   同时把这些 chunk 的 `chunks_by_id` 补齐 → 得到**派生检索池**。
2. **facts 层**：把来源批次的该格内容写进合成 `facts-workspace.json`。
3. **呈现层**：构基阶段**只记录每格的来源批次**（写入 `provenance.json`）；呈现层对照在**评估阶段**用来源批次的 HTML 定位，不在构基阶段拼 HTML。
4. 证据校验：用派生检索池做 `verifyEvidenceRefs`，确保每条 checklist item 的 `source_chunk_ids` 都能落到实处。

> ⚠️ **已知静默丢弃点**：`lib/checklist.mjs` 的 `pushItem` 会**丢弃没有 sourceChunkIds 的条目**（除非 `--allow-unverified`）。
> 所以合成后必须报告「因无证据被丢弃的条目数」，否则会静默丢内容。

## 6. Gate 处理：`ceiling` 模式

**已实现（2026-09-20）。** B3 的 `capability` 为 `ceiling`，走专用分支。

### 6.1 规则

- `capability` 增加取值 **`ceiling`**（B1 = `retrieval_and_facts`，B2 = `full`）。
- 该模式下 **Gate 全部跳过**：G2/G3/G4 状态为 `SKIPPED`，**数值原样保留**在 `report.gates.*` 里供诊断；
  G1 在提供 HTML 时同样为 `SKIPPED`（机械校验结果改写进 `gates.G1.mechanical_status`），未提供时为 `N/A`。
- `report.conclusion` 取新值 **`CEILING`**，**永不出现 `FAIL`**。
- 判据由新字段 **`report.coverage`** 承载（见 §6.2）。
- **只加分支，不动 B1/B2 现有判定逻辑**（不变量，见 §9）：`capability !== "ceiling"` 时
  report 结构与改动前**逐字段一致**，不新增 `coverage`。
- 理由：天花板下"没人能全覆盖"是正常状态，`FAIL` 结论对用户无意义。

### 6.2 覆盖率口径（`report.coverage`）

主口径是**覆盖率**，不是通过与否；`critical` 从 fail 条件降级为**缺口权重**
（`critical` 4 / `core-quality` 3 / `mid` 2 / `low` 1）。

| 指标 | 定义 | 用途 |
|---|---|---|
| `layers.<L>.rate` | 本层覆盖条目数 ÷ 全部天花板条目（273） | 离理想并集有多远 |
| `layers.<L>.weighted_rate` | 同上，按 criticality 加权 | **可跨参数组比较的主分数** |
| `layers.<L>.conditional.rate` | 本层覆盖 ÷ **上游已覆盖**（facts 的上游是 retrieval，render 的上游是 facts） | 衡量**这一层自己**漏了多少 |
| `fully_covered` | 三层全部覆盖的条目数 | 触及天花板的条目 |
| `weighted_coverage` | `(总权重 − 缺口权重) ÷ 总权重` | 整体离理想多远 |
| `gaps.items[]` | 每条缺口**只记最上游那一层**（`first_missing_layer`），按权重降序 | 缺口清单 |

#### 6.2.1 检索层 chunk 粒度口径（2026-09-21 新增，修订记录见 `rounds/P3-2026-09-20/LOG.md` §A3）

**背景**：上面的 `layers.retrieval` 是**条目级**的 —— 一条条目只要有任意 1 条证据入池就算命中。
在扩容后的 337-chunk 索引上它会**饱和**：8 个不同配额档位读数同为 `273 / 273`，
无法给参数排序，直接违反本节事实 2「绝对值不是问题，**区分度**才是」。

**新增字段**（只在天花板模式产出，非 ceiling 路径输出逐字段不变）：

| 字段 | 定义 | 用途 |
|---|---|---|
| `layers.retrieval.chunk_level.source` | `reading_pool` \| `attribution` | 说明下面几个数字用的哪套「入池」语义 |
| `unique_evidence_chunks` | 证据 chunk 去重后的入池数 / 总数 | **材料广度，跨参数组主排序依据** |
| `unique_critical_evidence_chunks` | 同上，限 critical 条目 | 硬门槛面是否被撑住 |
| `partial_credit_weighted_rate` | 逐条目按「已入池证据 ÷ 该条目全部证据」给部分分，再按 criticality 加权 | 容忍「只捞到部分证据」的中间态 |
| `fully_evidenced_weighted_rate` | 证据**全部**入池的条目加权占比 | **facts 层可写上界**（见下） |

**`fully_evidenced_weighted_rate` 的意义**：检索层是 facts 层的唯一上游，证据没进池的信息
不可能被写对（写了就是幻觉、触发 G4）。这条给出「若 agent 读全池，facts 层最多能覆盖多少」，
使检索层调参不必每轮都付一次长文阅读成本。

**两套「入池」语义必须显式区分**：`reading_pool`（chunk 在 `chunks_by_id` 里，= agent 能读到）是
天花板口径要的量；`attribution`（被它所属条目的目标/主题自己选中）是 B1/B2 的 CIR/N1/N2/Gate 用的
**归属正确性**语义，**跨目标携带的 chunk 会被它判为未召回** —— 实测在 t0 上低估 unique 1 条、
低估可写上界 **13.0 个百分点**（65.8% vs 78.8%），因此不能拿它当可写上界。
`computeCeilingCoverage` / `createReport` 因此新增可选入参 `retrievalWorkspace`；
拿不到阅读池时回退到 `attribution` 并在 `source` 字段如实标注。

两条必须记住的口径事实：

1. **`conditional` 不可省。** 只给无条件覆盖率时，facts 层没写的东西不可能出现在页面上，
   于是呈现层覆盖率会被 facts 层**锁死**（实测两者完全相同：`16/273`），完全看不出模板本身的问题。
   加了 `conditional` 后同一份报告的呈现层读作 `16/16 = 100%`——**模板无漏损，缺口全在上游**。
2. **分母是「8 批池的并集」，绝对值必然低。** 天花板要求 123 个 chunk，而任何单批 run 的池只有约 43 个
   （实测 0918-3：检索层 24.9% / facts 层 5.1% / 整体加权 3.0%）。**绝对值不是问题，区分度才是**——
   跨参数组比较时看的是同一批条目上的相对高低。
