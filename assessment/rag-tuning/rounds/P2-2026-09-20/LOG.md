# 第一部分 · 本轮所做的评估体系修订

> 两条修订均发生于 2026-09-20、P2 搜索开始之前，属本轮的**准备阶段**。
> 修订后的**当前有效规则**已并入 `INTENT.md`：E1 → §4.6 裁定纪律 / §4.8 每轮事实层的标准作业；

## A1. E1：facts 层补上裁定分流（2026-09-20）

**背景**：P1 基线实测发现，B1 的 facts 层判定存在系统性测量偏差 —— B1 的 36 条 checklist 文本**逐字抄自旧基线
`facts-workspace.json` 原文**（逐字命中 36/36），而 facts 层判定用字面子串匹配，导致任何重新生成的 facts
只要措辞不同就被判「丢失」（同一 36 条在新生成 facts 上逐字命中仅 2/36）。

**修订决定**（用户拍板）：不采用「只调检索层」「对齐旧措辞」「逐条人工」三条路线，改为**补上原本漏掉的裁定分流**。

**改动范围（仅分流，不碰判定算法）**：

| 文件 | 改动 |
|---|---|
| `scripts/assessment/rag-tuning/lib/facts_metrics.mjs` | `adjudication_needed` 追加 `uncovered_needs_review`（未覆盖但已召回）条目 |
| `scripts/assessment/rag-tuning/lib/adjudication.mjs` | 骨架尊重条目携带的 `current_assessment` |
| `test/assessment/facts_metrics.test.mjs` | 同步断言新契约 + 固定「检索层未召回项不进 facts 裁定队列」 |

**未改动**：覆盖判定算法、CIR/N1/N2 计算、Gate 判定、报告格式、CLI、基准文件、工作流上下游。

**与不变量 4 的关系**：本修订**不放松判定规则**，只把原本被漏分流的条目纳入 `RAG_TUNING_TECHNICAL_PLAN.md` §5.3
既有的裁定通道。覆盖结果仍由 `coverage_overrides` 逐条决定，且每条必须写明理由、可被人工推翻并重跑。
不变量 4「不修改判定逻辑来让结果好看」仍然有效。

## A2. E2：M3 改用证据 chunk 为单位（2026-09-20）

**背景**：P1 基线实测暴露 M3 不可用，两个独立缺陷：

1. **粒度不可通约**：B1 基准条目是粗粒度摘要，生成层按字段展开成条目，一条基准 ≈ 3~4 个候选条 → `new_items` 虚增到 162 条，其中 146 条只是既有信息的细化拆分。
2. **判定不可自动化**：判定「某条候选是否携带基准没有的新事实」需要阅读理解。实测三种自动比较全部失败：

| 方法 | 实测结果 |
|---|---|
| 字符 bigram 包含度 | 已知重复项 0.65 / 0.57，但 137/162 落在 <0.20 灰区，无法设阈 |
| 整段命中（复用 facts 层 `textTokenRatio`） | 已知重复项只到 0.25，比 bigram 更脆 |
| embedding 余弦（本地 `qwen3-embedding:0.6b`） | 已知重复项 `B1-new-0015`=0.694，已知真实新增「丁达尔光束」=0.679 → **同分不可分** |

**修订决定**（用户拍板）：不改判定算法、不引入语义模型，改为**换度量单位**——从「条」换成「证据 chunk」，按 `(target_type, target_name, theme)` 分组聚合。依据：候选证据是**分组级**的（实测同分组内所有候选共享同一组 chunk id），把一条基准拆成 3 条候选 chunk 集合不变，粒度虚增被结构性消除。

**改动范围（仅新增度量层）**：

| 文件 | 改动 |
|---|---|
| `lib/report_writer.mjs` | 新增 `computeNewItemEffect()` 与分组新颖度辅助函数；`createNewItemDeltas` 的 `effective_new` 不再恒为 `true`，改为「该分组是否含基准未使用过的证据」；`createDeltas` 接收并落地 `new_item_effect`；`createReport` 输出 `metrics.M3`；markdown 增加「M3 有效新增（证据单位）」章节 |
| `evaluate_run.mjs` | 接线 `computeNewItemEffect` |
| `test/assessment/report_writer.test.mjs` | 断言 M3 契约 + 新增「粒度虚增不影响 M3」用例 |

**未改动**：`new_items` 的生成逻辑、`candidateAlreadyCovered` 去重规则、覆盖判定、CIR/N1/N2 计算、Gate 判定、CLI、基准文件、工作流上下游。`raw_candidate_items`、`effective_new_items` 保留在报告里但标注为「诊断，不计分」。

**与不变量 4 的关系**：本修订**不放松任何判定**，只补一个免疫粒度的度量口径。Gate 判定链路未触碰。

**遗留**：`effective_new_items`（146）仍是条目级、粒度不齐，**不可跨轮比较**；如需语义级「有效新增条数」，需另起一轮把分组级判定移入 agent 裁定（当前未做，P2 不依赖它）。

## 2.3 本轮确认的机制事实（供后续轮次复用）

1. **L2 主题词表之外的三个旋钮中，只有两个有效**：`recallWidth`（窗口）与 rerank 主题范围（`--rerank-all-themes`）。
2. **rerank 阈值轴在本语料上完全失效**：0.70 / 0.80 / 0.90 三档结果逐指标相同。
3. **L3 降权系数是承重结构**：归零使 R2 从 0.8136 跌到 0.7458（−45 chunk）。L3 不应再进入搜索空间。
4. **top-k 决定桶容量，`maxPlaceChunks` 帽值未触顶**：只抬 top-k 与「抬 top-k + 抬帽」结果完全相同；瓶颈是桶内排序截断，不是总量帽。
5. **窗口不是越大越好**：12→16→24 有效，24→30→56 反向退化（读量上升、召回下降）。
6. **命名差异不构成召回障碍**：索引标注 `九洞天`、facts 目标名 `九洞天景区`，实体门控全部通过；已排除「命名导致丢失」这一假设。

## 2.4 判据标定问题 → 已修订（见 `INTENT.md` §1.3.1）

实测「有效新增」与「读取量」近似成正比（斜率约 0.8 个 M3 chunk / 1% 读取量）。由此：

- §1.3 增密型的 `M3 novel_evidence_chunks ≥ 基线 + 3`（即 ≥ 43），在「读取量 ±10%（池 ≤ 90）」窗口内**结构性不可达**：需 `novel_pool_chunks ≥ 43` 且吸收率 ≥ 100%，而实测吸收率上限约 75%；按 75% 反推需要池容 ≥ 95（读取量 ≥ +16%），与 ±10% 窗口互斥。
- §1.3 增密型的 `M1 或 M2 提升 ≥ 10%` 同样不可达：M1/M2 的分母就是池容，池容不变时上限基本锁死。

**这不是要求放宽判定**（不变量 4 仍然有效），而是一条判据标定问题。

**处置**：2026-09-20 经用户批准，已按 `INTENT.md` §1.3.1 修订——增密型门槛从「facts 层 M 指标提升」改为「检索层关键召回率 `R1` 相对提升 ≥ 10%」，并附「facts 层不退化」约束守住底线。

**一个未被采纳的替代口径**：曾考虑改为「检索层密度提升」，即 `ref_in_pool ÷ 池容` 相对提升 ≥ 10%。放弃的原因是该口径会把 F2 选为最优（F2 = +26.6%，F3 仅 +5.6%），而 F2 已知存在**真实材料损失**（city:宜宾 foods/lodging 两桶归零、兴文石海「游船不到 3 分钟」承载 chunk 掉出池）。密度口径只看「池子里的有效引用密度」，看不见「桶被清空」这类结构性塌陷，与「不退化」的意图冲突。
