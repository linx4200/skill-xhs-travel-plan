# RAG 调参评估体系 PRD

## 1. 产品目标

为项目 `scripts/rag/` 的参数调优建立一套长期可复用、可复现、可量化、可诊断的离线评估体系。该体系用于判断新参数产出是否相对已冻结的满意基准退化，并定位有效信息减少发生在检索、重排、资料整理还是最终呈现阶段。

评估体系服务于“景点/城市资料整理”类 RAG 输出。目标不是直接评价旅行路线、小红书正文或个人笔记的文案表现，而是评价资料整理结果是否保留并呈现了足够的有效信息，尤其是能否讲清景点或城市为什么值得去、适合谁、玩多久、是否绕路、有哪些风险和替代方案。

## 2. 适用范围

评估体系适用于以下参数域的调优和回归检查：

- 主题词表：`PLACE_THEMES`、`CITY_THEMES`
- 打分与降权：`RAG_SCORING`
- 配额与 top-k：`RAG_RETRIEVAL_DEFAULTS`
- 重排：`RAG_RERANK_DEFAULTS`

评估体系是离线工具，不进入 `SKILL.md` 描述的攻略生成主流程，不改变现有 RAG 分支行为。

## 3. 用户与使用场景

主要用户是执行 RAG 调参和质量回归的 agent。用户只参与两类决策：

1. 首次建立基准清单后审核一次，确认信息块拆分和重要性分档合理。
2. 每次评估产出后查看 `PASS`、`PASS_WITH_NOTES` 或 `FAIL` 结论，以及必要的调参建议。

典型使用场景：

- 日常调参：每改一组参数后运行快评，检查关键信息是否退化。
- 收敛确认：确定候选参数前运行全评，检查完整诊断、有效新增、越界事实、资料整理质量和呈现质量。
- 回归保护：后续修改 RAG 代码或参数时复跑评估，防止满意基准中的有效信息丢失。
- 基准升级：出现稳定优于当前基准的新产出时，将有效新增逐条合并进基准清单并留痕。

## 4. 核心原则

### 4.1 执行事实保底，游玩价值决定好坏

评估体系同时保护两类价值：

- 信息保有底线：门票、交通、安全、人流、无障碍等执行事实属于关键底线，关键项零丢失。
- 有效信息质量：看点、为什么值得去、适合谁、玩多久、是否绕路、替代方案、风险避坑等内容用于判断输出是否真正有用。

基础事实不能替代游玩价值和实用判断。一个产出即使保留了门票和交通信息，如果缺少“为什么值得去”“适合什么人”“停留多久是否值得”等判断，也只能视为低质量或需要复查的产出。

### 4.2 分层诊断优先于单一总分

评估结果必须能回答：

- 哪些地点或城市、哪些主题丢失了有效信息。
- 丢失发生在召回、重排、配额截断、资料整理还是最终呈现阶段。
- 该问题应通过调 RAG 参数解决，还是属于资料整理层或呈现层问题。
- 下一步参数应向哪个方向调整。

系统不设置单一综合总分。所有结论以硬门槛、分层指标、1-5 分语义评分和逐条证据共同构成。

### 4.3 基准是最低满意线

两份满意输出作为最低满意线，而不是满分样例。新产出达到基准水平才算合格；超过基准且有材料证据支撑的新增信息，才算有效优化。

基准清单只需建立一次，之后长期复用。出现更好的输出时，基准通过“逐条合并最优”的方式升级；清单只升不降，历史评估报告引用的基准版本不得被改写。

### 4.4 证据访问受控

评估流程允许通过专门 assessment 工具或脚本读取 `rag-index.json` 的 chunk 原文，用于有效新增、越界事实和证据归因核验。agent 不应临场自由翻阅 chunks、text 或 embedding，也不把 `rag-index.json` 作为日常手工诊断入口。

调参评估运行必须生成并归档 `retrieval-log.json`。缺少该日志时，评估只能降级执行，不能输出完整归因结论。

## 5. 基准与输入

### 5.1 基准对象

评估体系维护两份互相独立的基准清单：

| ID | 路径 | 能力位 | 用途 |
|---|---|---|---|
| `B1` | `output/rag-e2e-smoke/` | `retrieval_and_facts` | 小样本检索层 + 资料整理层基准 |
| `B2` | `outputs/2026-guoqing-self-drive-plan-20260907/` | `full` | 全量检索层 + 资料整理层 + 呈现层基准 |

两份基准地位平等，各自代表该输入下的满意水平。两份基准不共用阈值，不互相比较。

`facts-workspace.json` 是资料整理层的主要评估对象。内容覆盖、游玩价值、实用决策、风险避坑和证据吸收优先基于 `facts-workspace.json` 评分。

最终 HTML 是呈现层评估对象，用于检查结构完整、跨页归位、重复展示、链接、图片和本地资源等呈现质量。没有 HTML 时，只将呈现层指标记为 `N/A`，不得把呈现层缺失记为内容缺失。

`B1` 没有最终 HTML，但可以用 `facts-workspace.json` 评估资料整理层；呈现层指标记为 `N/A`。

`B2` 支持完整评估，但若历史产物缺少 `retrieval-log.json`，诊断明细需要依赖新评估运行补齐日志。

### 5.2 评估输入

一次完整评估需要以下输入：

- 基准清单：`assessment/rag-tuning/baselines/*.checklist.json`
- 新产出：`retrieval-workspace.json`
- 调参日志：`retrieval-log.json`
- 资料工作区：`facts-workspace.json`
- 最终 HTML：有呈现层评估时必需
- 参数快照：`params.json`
- 原始证据访问接口：由 assessment 工具或脚本受控读取 `rag-index.json` chunk 原文

正式 RAG 主流程不默认生成 `retrieval-log.json`；调参评估流程必须生成并归档该日志。

## 6. 基准清单

### 6.1 信息块定义

清单条目是一条可独立成立、可独立决策的出行信息。粒度落在段落或信息块级，不做逐词差异比较。

算作独立条目：

- 一个可执行要点，例如停车入口、预约方式、适合时段。
- 一个数值事实，例如门票、车程、开放时间。
- 一条风险提示，例如老人不建议走全程台阶。
- 一条体验理由，例如某观景台值得专门早起看日出。
- 一个实用判断，例如是否值得绕路、适合停留多久、适合什么人群。

不收入清单：

- 纯排版文本、标题、导航、免责声明。
- 情感词、语气助词、没有证据支撑的泛泛判断。
- 同一事实的重复表达。

### 6.2 清单覆盖面

清单收入基准输出里的所有有效信息点，包括执行类、体验类、决策类和风险类信息。覆盖面全收，权重与容差分层处理。

信息块必须包含：

- `id`
- `text`
- `domain`
- `place` 或 `city`
- `theme`
- `criticality`
- `source_chunk_ids`
- `evidence_ref`
- `added_at`
- `source_run`

缺少 `criticality`、`source_chunk_ids` 或 `evidence_ref` 的条目不得进入正式清单。

## 7. 评估模型

评估模型分为三层：

- 检索层：判断目标地点或城市、主题和 source chunk 是否进入阅读池。
- 资料整理层：以 `facts-workspace.json` 为主，判断已召回证据是否被吸收为结构化资料。
- 呈现层：以最终 HTML 为主，判断结构、归位、重复、链接、图片和本地资源是否符合发布要求。

资料整理层是内容评分的主层。呈现层不得替代资料整理层，也不得因为 HTML 缺失而否定 `facts-workspace.json` 中已经存在的内容。

### 7.1 硬门槛

硬门槛用于判定产出是否可接受：

| Gate | 条件 | 结果影响 |
|---|---|---|
| G1 呈现机械校验 | HTML 产物通过结构、链接、图片、本地资源检查 | 有 HTML 时不通过则 `FAIL` |
| G2 关键底线零丢失 | critical 条目在检索层和资料整理层均不得丢失；有 HTML 时呈现层也不得丢失 | 不通过则 `FAIL` |
| G3 高置信归位错误为 0 | 事实不得写到错误日期、地点或城市下；优先检查 `facts-workspace.json`，有 HTML 时同步检查呈现层 | 不通过则 `FAIL` |
| G4 关键类越界事实为 0 | 关键事实必须能被材料证实 | 不通过则 `FAIL` |

无 HTML 的评估跳过 G1 和呈现层指标，并显式标记 `N/A`。只要存在 `facts-workspace.json`，资料整理层指标必须执行。

### 7.2 语义评分

语义评分采用 1-5 分刻度。每个维度必须输出分数、证据和扣分理由。

通用锚点：

| 分数 | 语义 |
|---|---|
| 1 | 缺失或基本不可用 |
| 2 | 有少量相关信息，但关键价值缺失 |
| 3 | 基本可用，达到最低满意线 |
| 4 | 覆盖充分，能支持清晰判断 |
| 5 | 信息完整、判断清楚，并明显优于最低满意线 |

必评维度：

| 维度 | 关注点 |
|---|---|
| 信息覆盖 | 基准清单中的有效信息是否被保留 |
| 游玩价值 | 是否讲清看点、亮点、最佳季节或时段、为什么值得去 |
| 实用决策 | 是否讲清适合谁、玩多久、是否绕路、路线衔接、替代方案 |
| 风险避坑 | 是否保留排队、商业化、天气、交通、体力、人流等限制 |
| 证据吸收 | 已召回证据是否进入 `facts-workspace.json`；有 HTML 时再检查是否进入最终呈现 |
| 可执行性 | 读者能否直接据此做行程判断或现场决策 |

语义评分不推翻硬门槛结论，但用于区分 `PASS` 和 `PASS_WITH_NOTES`，并用于判断是否存在有效优化。

### 7.3 指标体系

评估报告至少包含以下指标：

- CIR：关键信息保有率，critical 条目必须达到 100%。
- R1：关键 chunk 召回率。
- R2：总体 chunk 召回率。
- R3：主题空池率。
- R4：丢失归因分布。
- N1：关键条目丢失数。
- N2：非关键主题丢失数。
- N3：归位错误数。
- N4：有效新增条目数。
- N5：越界事实数。
- N6：冗余率。
- N7：可执行性 1-5 分。
- N8：结构完整度。

指标用于诊断和趋势比较，不合成为单一总分。

N1-N7 优先基于 `facts-workspace.json` 计算或判定；存在最终 HTML 时，同时检查呈现层是否相对 `facts-workspace.json` 发生内容丢失、归位错误、重复或结构缺失。N8 仅在存在最终 HTML 时执行。

### 7.4 判定档位

| 档位 | 条件 |
|---|---|
| `PASS` | 所有适用 Gate 通过，主题丢失在容差内，语义评分不低于最低满意线 |
| `PASS_WITH_NOTES` | Gate 通过，但存在非关键主题超容差丢失、软性指标下滑或语义评分不足 |
| `FAIL` | 任一适用 Gate 不通过 |

## 8. 主题分档与容差

主题分档同时体现执行底线和有效信息质量。

| 分档 | 主题或信息类型 | 容差 |
|---|---|---|
| critical | 门票、交通、安全、人流、无障碍等执行底线；关键风险；关键事实归位 | 零丢失 |
| core-quality | 看点、为什么值得去、适合谁、玩多久、是否绕路、路线衔接、替代方案 | 允许极小波动，但低于基准满意线时必须 `PASS_WITH_NOTES` 或 `FAIL` |
| mid | 一般路线建议、住宿、城市 notes、备选点、drawbacks | 小幅容差 |
| low | 设施、附近补充、美食等辅助信息 | 较宽容差 |

`core-quality` 不作为基础事实的替代项，也不得被简单归入 low。它是判断产出是否“好”的核心维度。

## 9. 归因规则

对每条丢失信息先做检索层归因，再做资料整理层和呈现层归因。归因码互斥，按命中顺序确定：

| 归因码 | 含义 | 指向 |
|---|---|---|
| `keyword_miss` | source chunk 未进入对应 theme 候选集 | 主题词表 |
| `score_low` | chunk 进入候选但分数低于截断阈值 | 打分与降权 |
| `topk_cut` | chunk 有分但排在 top-k 外 | top-k 参数 |
| `quota_dropped` | chunk 被总量配额挤掉 | place/city 总配额与主题顺序 |
| `rerank_drop` | rerank 阈值过滤了高价值 chunk | rerank 阈值 |
| `facts_drop` | chunk 已进阅读池但未进入 `facts-workspace.json` | 资料整理层 |
| `render_drop` | 信息已进入 `facts-workspace.json` 但未进入最终 HTML | 呈现层 |
| `unknown` | 证据不足或规则无法解释 | 需要人工复查 |

报告必须为每一个出现过的归因码给出涉及主题、涉及参数、建议调整方向和证据。出现 `facts_drop` 或 `render_drop` 时，报告必须明确该项与 RAG 参数无关，不应靠调检索参数解决。

## 10. 评估档位

### 10.1 快评

快评用于日常调参循环。目标是分钟级判断是否退化。

快评必须检查：

- 关键清单条目是否全量保留。
- critical 主题是否零丢失。
- R1、R2、R3、R4。
- 高置信归位错误。
- 有 HTML 时的机械校验。
- `facts-workspace.json` 中的关键内容保有情况。

快评可以跳过有效新增、越界事实、冗余率、HTML 呈现层细查和完整语义评分，但必须输出是否需要全评复查。

### 10.2 全评

全评用于里程碑、参数收敛和基准升级候选评审。

全评必须检查：

- 所有 Gate。
- 全部 R 指标和 N 指标。
- `facts-workspace.json` 资料整理层评分。
- 有 HTML 时的呈现层评分。
- 1-5 分语义评分。
- 有效新增和越界事实。
- 归因到参数的调参建议。
- 基准升级候选条目。

## 11. 输出物

评估体系输出以下文件：

```text
assessment/rag-tuning/
├── baselines/
│   ├── B1-rag-e2e-smoke.checklist.json
│   └── B2-20260907.checklist.json
├── runs/
│   └── <YYYYMMDD-HHmm>-<baseline_id>-<tag>/
│       ├── report.md
│       ├── report.json
│       ├── deltas.json
│       ├── params.json
│       ├── facts-workspace.json
│       └── retrieval-log.json
└── CHANGELOG.md
```

`report.md` 面向人阅读，必须包含：

1. 结论：`PASS`、`PASS_WITH_NOTES` 或 `FAIL`
2. 基准与能力位
3. 参数变更
4. Gate 结果
5. 指标面板
6. 1-5 分语义评分
7. 丢失条目明细
8. 有效新增明细
9. 归因到参数的建议
10. 基准变更记录

`report.json` 面向机器读取，字段必须与 `report.md` 的核心结论一致。

`deltas.json` 保存逐条丢失、新增、归位错误和越界事实，并标明发生在检索层、资料整理层还是呈现层。

`params.json` 保存本次生效的完整参数快照。

`facts-workspace.json` 保存本次评估使用的结构化资料产物，是资料整理层评分的主要对象。

`retrieval-log.json` 保存本次调参评估的召回、过滤、向量相似度、rerank 概率、阈值、kept、filtered、out_of_window 等诊断信息。

## 12. 基准升级

候选产出满足以下条件时，可进入基准升级流程：

- 全评结果为 `PASS`。
- 存在材料可证实的有效新增。
- 有效新增不是现有清单条目的同义重复。
- 与现有条目不存在未裁定冲突。

升级流程：

1. 对候选产出执行全评。
2. 为每条有效新增生成清单条目候选。
3. 通过 assessment 工具核对 `rag-index.json` chunk 原文。
4. 去除语义重复项。
5. 标记冲突项并等待用户裁定。
6. 合并通过项，递增清单版本。
7. 写入 `CHANGELOG.md`。

清单条目一经加入不得因某次新产出跑不出而删除。确需删除时，必须由用户显式确认，并记录删除原因。

## 13. 非目标

本评估体系不做以下事情：

- 不做多组参数排行榜或批量扫描比较。
- 不用单一综合总分替代分层诊断。
- 不把基准当成满分样例。
- 不建材料真值清单作为常规参照系。
- 不要求用户每次逐条核对。
- 不让 agent 自由手工翻阅 `rag-index.json` chunks/text/embedding。
- 不把评分流程写入主攻略生成链路。

## 14. 验收标准

PRD 对应的评估体系完成后，应满足以下标准：

- 能基于 B1 和 B2 建立独立基准清单，并标注能力位。
- 能对新产出给出 `PASS`、`PASS_WITH_NOTES` 或 `FAIL`。
- 能稳定判断 critical 条目是否零丢失。
- 能输出 1-5 分语义评分，并说明证据和扣分原因。
- 能区分检索层丢失、资料整理层丢失和呈现层丢失。
- 能在没有 HTML 时基于 `facts-workspace.json` 完成资料整理层评估，并将呈现层标记为 `N/A`。
- 能基于 `retrieval-log.json` 归因到关键词、打分、top-k、配额或 rerank。
- 能在缺少 `retrieval-log.json` 时降级评估，并明确“不输出完整归因”。
- 能核验证据支撑的有效新增和越界事实。
- 能输出面向人阅读的报告和面向机器读取的结构化结果。
- 能通过版本化清单和 `CHANGELOG.md` 支持基准只升不降。
