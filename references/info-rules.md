# 信息提取与内容取舍规则

本文件用于判断哪些信息可以成为攻略事实，以及这些事实应该放到 `facts-workspace.json` 的哪个位置。JSON 字段契约见 [data-contracts.md](data-contracts.md)；结构化脚本流程见 [structured-generation-workflow.md](structured-generation-workflow.md)。

生成 HTML 前还必须按 [pre-render-online-research.md](pre-render-online-research.md) 做独立的联网需求判断。除用户另行明确授权外，只能查询该 reference 白名单中列出的信息；不要联网补充营业时间、票价、天气、交通时长或图片。

## 总体原则

读取用户提供的输入文件夹，把其中的文本材料统一视为输入材料。先按地点、主题和用途归类，再压缩成可执行信息；不要把相关句子机械摘录成连续列表。

只提取材料中明确出现、或可从用户路线和材料上下文直接归纳的信息。不要用常识、想象、营销式表达或未经授权的联网结果补足空白。成文时直接陈述整理后的事实和判断，不要使用 `材料指出`、`材料中的`、`材料还提到` 这类旁白式来源表述。

同一条信息只放在最适合执行的位置，避免在首页、每日详情页、城市详情页、整体准备、确认清单中反复重复。优先级通常是：

1. 只影响某个景点执行的信息，放入 `places.<景点名>`。
2. 只影响某一天行程的信息，放入 `trip.days[].timeline`、`notes` 或 `confirmations`。
3. 城市级、跨景点且有独立增量价值的信息，放入 `cities.<城市名>`。
4. 跨天通用准备、风险或确认事项，放入 `global_notes` 或 `confirm_before_departure`。

## 路线解析规则

解析用户路线规划，提取每天的日期、城市、景点和活动，得到 `route-structure.json.days` 与候选城市清单。具体字段见 [data-contracts.md](data-contracts.md)。

`route_places` 只放用户路线中明确出现的真实景点/景区名称。必须排除城市名、住宿点、停车场、游客中心、售票处、入口、公交站、车站、码头、餐厅、酒店、商场和普通导航点。

停车场、游客中心、入口、码头、车站、售票处等如果与某个景点相关，应放进该景点的交通、到达、停车、购票或实用提醒中，不要作为独立景点标题。

每日景点详情只包含用户路线中的景点。如果用户路线没有提到当天景点，对应每日页面可以不生成“当日景点详细信息”章节。

同一景点跨多天出现时，详情放在首次实际游玩的每日详情页；后续页面只做短句引用，除非后续当天有不同玩法、入口、路线或新的执行风险。

## 材料分类规则

整理材料时重点识别以下事实类型：

- 地点：城市、区域、景点、景区、餐厅、酒店、交通点、购物点、观景点。
- 执行信息：营业时间、门票、预约、优惠、交通、停车、排队、建议游玩时长、入口、寄存、洗手间。
- 体验评价：优点、缺点、避坑、负面体验、安全提醒、注意事项。
- 玩法信息：推荐路线、拍照点、最佳游玩时段、不同玩法、替代方案。
- 特殊人群和环境：老人、小孩、体力、天气、高海拔、安全相关提醒。
- 本地照片：只使用输入材料文件夹中的本地图片；优先识别 `photos/景点名/` 这类目录归属。

## 缺失、冲突和不确定信息

字段只有在材料有有效信息，或会影响出行决策时才写。没有有效依据时不要硬凑。

只有以下情况才写 `材料未说明`：

- 该信息会直接影响当天执行，例如明确需要预约、购票、赶时间、避开限流或确认开放状态。
- 材料暗示存在风险或限制，但没有给出关键细节。

材料没有提到的普通信息直接留空，让渲染脚本跳过对应小节。

不同材料对同一事实说法冲突，且冲突会影响执行时，写入对应景点或城市的 `conflicts`、`notes` 或当天 `confirmations`。不要自行判断哪一条“最新”或“正确”，除非用户授权联网核验，或 [pre-render-online-research.md](pre-render-online-research.md) 明确允许查询该项。

## 每日行程规则

`trip.days[].summary` 写当天执行重点，不写空泛宣传。

`trip.days[].timeline` 写当天行程顺序，可写景点、车程、活动或关键转场。不要安排早餐、午餐、晚餐、用餐时间或餐厅停留点，除非用户明确要求安排餐饮。

`trip.days[].notes` 只写当天特有注意事项，例如当天体力、天气、赶路、停车、限流、安全风险。

`trip.days[].confirmations` 只写当天出发前或到达前必须确认的事项，例如预约、票务、开放、交通管制、停车入口。

## 景点信息规则

以单个真实景点或景区为单位填充 `places.<景点名>`。景点名只写真实景点/景区名称，不要把停车场、游客中心、入口等设施拼进标题。

景点摘要、看点、缺点、开放时间、票务、时长、内部路线、玩法、实用信息、注意事项、冲突和照片分别填入 [data-contracts.md](data-contracts.md) 中定义的对应字段。以下规则优先级最高：

- 材料未说明的信息不能算作缺点。
- 营业时间、票价、预约方式、优惠政策只有材料明确写明时才填；如果它会影响当天执行但材料未说明，才写 `材料未说明`。
- 建议游玩时长只有材料有明确时长，或可从用户路线安排中合理归纳时才写；没有有效依据时留空。
- 景区内部多条路线要分别整理适合人群、顺序、优缺点。
- 出现不同玩法或游玩方式时，必须拆成独立方案处理，例如常规景区、外围点位、不进景区看风景、不同入口、不同导航点。
- 本地照片只使用输入材料文件夹中的图片，并按景点归属展示到对应每日景点详情中。没有对应照片的景点直接留空，渲染时跳过照片区域。
- `source_files` 只用于 agent 读取原文，不要写进最终正文。

## 城市信息和 include 判断

城市汇总不是每个城市必写。只有排除重复内容后仍有独立、具体、可执行的信息，才在首页城市汇总中列出该城市，并生成对应城市详情页。

使用结构化流程时，城市页是否生成由 `facts-workspace.json` 中的 `cities.<城市名>.include` 固化；不使用结构化流程时，也沿用同一判断标准。

先排除以下内容：

- 已经在当天安排、每日景点详情、整体准备或出行前确认中写过的信息。
- 只是说明城市角色的句子，例如“这里是出发地”“这里是住宿地”“这里是某景点所在地”。
- 只有景点名字，但没有具体介绍、玩法、交通、注意事项的信息。
- 需要大幅改变当前路线或住宿安排才成立的建议。
- 只有 `材料未说明` 或 `具体玩法未说明` 的内容。
- 纯粹为了凑城市章节而写的概览、餐饮、住宿、交通空话。

排除后，满足以下任一条件，才把 `include` 设为 `true`：

- 至少有 2 类对行程有用的城市级信息，例如明确美食、住宿区域、停车/交通风险、天气/海拔提醒、备选景点库。
- 至少有 2 个可作为备选的城市景点，且每个都有具体介绍。
- 该城市承担住宿、中转或连续游玩基地功能，且材料提供了具体住宿、停车、补给或交通信息。
- 有明确城市级风险会影响执行，例如山路、夜间驾驶、停车困难、高反、温差、限行、景区分散等。

通过判断后，只写对本次行程有帮助、且材料中有实质内容的信息：

- `summary`：首页城市汇总中的 1 句话摘要；只在 `include=true` 时填写。
- `overview`：1-3 句话说明这个城市在本次行程中的角色；不能只是“这里是出发地/住宿地/某景点所在地”。
- `backup_places`：输入材料中该城市出现、但没有作为每日景点详情完整展开的备选景点；只介绍景点本身，不强行建议加入当前路线。
- `foods`：材料中出现的餐厅、菜品、夜市、小吃、避坑餐饮。不要把餐饮写进当天 timeline，除非用户明确要求安排餐饮。
- `lodging`：材料中提到的住宿区域、酒店、民宿、交通便利性和注意事项。
- `transport`：只列出符合用户出行方式的信息；自驾只写停车、路况、导航、限行等相关信息，公共交通只写班次、换乘、站点等相关信息。
- `shopping`：购物点、伴手礼、市场、商业街及避坑信息。
- `notes`：城市级风险、天气、海拔、体力、安全、文化习俗、禁忌和其他注意事项。

没有实质内容的小节直接留空。不要为了让城市页显得完整而填空话。`source_files` 只用于 agent 读取原文，不要写进最终正文。

## 全局提醒和出发前确认

跨天通用信息只有材料中有实质内容、且对本次行程有帮助时才写。

可写入 `global_notes` 的内容包括：

- 必带物品：证件、衣物、药品、防晒、防雨、高海拔用品、儿童/老人用品等，必须说明为什么要带。
- 天气与穿衣建议：只整理材料中已有的天气、温度、季节、海拔或衣物建议。
- 交通与住宿总提醒：只列出符合用户出行方式的信息。
- 文化、习俗、禁忌和安全提醒。
- 贯穿多天的体力、老人、小孩、高反、安全风险。

更适合放到具体景点、某一天或某个城市的信息，不要为了首页完整而重复写进 `global_notes`。

`confirm_before_departure` 只写真正需要出发前确认或提前处理的事项，例如预约、购票、实名、限流、开放状态、天气、道路、交通管制、停车入口、班次、高海拔或老人小孩安全准备。普通建议、泛泛提醒、已经在某个景点或当天可以现场处理的信息，不要放进 `confirm_before_departure`。
